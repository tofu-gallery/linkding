# Tofu gallery copy

This repository is Tofu's copy of **sissbruecker/linkding** (licence: MIT), listed in Tofu's app gallery as **private bookmarks**: linkding, where you keep your own bookmarks with tags, notes and an unread mark, search them, save searches as bundles, and add to them from a browser extension, a bookmarklet or its REST API.

- `master` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` mark the versions the gallery points to. The current pin is `pin/2026-10-25.1`.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/sissbruecker/linkding at `27b7303baf41bb28babc610ac8eaa486e1ddfab5` (2026-09-13, v1.47.0).

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` is Tofu's own, after the `linkding` target of upstream's `docker/default.Dockerfile`, in three stages:
  1. `node:22-alpine`: `npm ci` and `npm run build` (esbuild) make `bookmarks/static/bundle.js` and the two theme stylesheets, which the repository does not commit.
  2. `python:3.13.7-slim-trixie` with build tools: `pip install uv==0.8.13` (upstream's uv version), then `uv sync --frozen --no-dev --group postgres` installs `uv.lock` into `.venv`. uwsgi (with PCRE, for its internal routing) and psycopg's C implementation are compiled against libpq here, as upstream does; every other locked package has a Linux wheel.
  3. `python:3.13.7-slim-trixie` with upstream's runtime packages (`media-types`, `libpq-dev`, `libssl3t64`, `libpcre2-8-0`): the virtualenv, the built scripts and styles, the application code, then `python manage.py collectstatic --noinput`.
- Left out compared with upstream's image: the SQLite ICU extension (it is only for SQLite), the `HEALTHCHECK` (Tofu checks the address itself), `curl` (only that check used it), uv's install script (uv comes from PyPI) and the `linkding-plus` image's Chromium and uBlock (HTML snapshots, see "What works differently on Tofu").
- The image sets `DJANGO_SETTINGS_MODULE=bookmarks.settings.tofu`: Tofu's `bookmarks/settings/tofu.py`, which takes upstream's production settings (`prod.py`, which imports upstream's placeholder `custom.py`, unchanged) and changes only what is listed under "What Tofu changes". uwsgi, `manage.py` and the background tasks all read it. Upstream's development and test settings (`dev.py`) do not import it. The image removes `bookmarks/settings/dev.py` (upstream's `.dockerignore` already leaves it out), so `bookmarks.settings` can never fall back to the development settings, which turn `DEBUG` on.
- `tofu-entrypoint.sh` is the image's `CMD`, run through `/bin/sh`. It does what upstream's `bootstrap.sh` does:
  1. `PORT`, which Tofu sets (80 without it), becomes `LD_SERVER_PORT`, and the server listens on `0.0.0.0` unless `LD_SERVER_HOST` is set.
  2. It makes upstream's `data/` folders and runs `manage.py generate_secret_key` (upstream's key file, which Tofu's settings do not use; see "The secret key").
  3. `manage.py migrate --noinput`, retried up to five times five seconds apart while a new database is still starting.
  4. `manage.py enable_wal` (upstream's; it does nothing on PostgreSQL).
  5. `manage.py tofu_close_data_api` (see "The database's Data API"). A failure is logged and the start goes on.
  6. `manage.py create_initial_superuser` (upstream's), with `LD_SUPERUSER_NAME` set to `admin` when only `LD_SUPERUSER_PASSWORD` is set (see "The first account").
  7. As root, it gives `data/` to `www-data`, then `exec supervisord -c supervisord-all.conf`.
  Upstream's `migrate_tasks` is left out: it moves the background tasks of a linkding older than its Huey queue out of a SQLite database a copy never has.
- Processes: supervisord, with upstream's `supervisord-all.conf`, runs uwsgi with upstream's `uwsgi.ini` (2 processes with 2 threads each; it serves `/static/` itself) and the Huey consumer for background tasks. Both write to the container's output, so the app's runtime log on Tofu shows requests, background tasks and errors. Upstream's default start instead sends the background tasks' output to `background_tasks.log` on the disk.
- The image has no `USER` line, so the container starts as root, which may listen on port 80, and supervisord starts uwsgi as root. Upstream's `uwsgi.ini` names `www-data` (`uid`, `gid`), and by default uwsgi's master drops to it early in its start, before its HTTP router binds the `--http` address. As `www-data` it could not bind port 80 (Linux keeps ports under 1024 for root): uwsgi would exit and nothing would answer. Upstream's image listens on 9090, where that never shows. So the image sets `UWSGI_DROP_AFTER_INIT=true` (uwsgi reads `UWSGI_*` variables as options, as upstream's image does with `UWSGI_MAX_FD`): the master binds `PORT` and its internal socket as root, starts Python, and then drops to `www-data`, before it loads linkding. linkding's code, the two workers and the HTTP router process all run as `www-data`. supervisord runs the background tasks as `www-data`, as upstream's configuration says. Nothing in the image runs a file from the repository directly: the start script goes through `/bin/sh`, everything else through `python`, `npm`, `uv` or `bash -c`.
- Database: PostgreSQL, the app's Tofu database, read from `DATABASE_URL`. The tables come from Django's migrations, which run at every start (76 on a new database). The repository has no `supabase/migrations` folder, so Tofu applies no SQL of its own.
- Environment: Tofu sets `PORT` and `DATABASE_URL`, and a gallery copy saves `LD_CSRF_TRUSTED_ORIGINS` set to the copy's own address. The copy starts with nothing set by hand. Signing in needs one hidden value the owner saves, `LD_SUPERUSER_PASSWORD` (see "The first account"). Settings an owner may add: `LD_SUPERUSER_NAME`, `LD_SECRET_KEY` (hidden), and upstream's other options (https://linkding.link/options/), such as OIDC sign-in; `LD_DB_ENGINE` and the other `LD_DB_*` settings replace `DATABASE_URL` when `LD_DB_ENGINE` is set.
- Upstream's files for other setups (`docker/`, `docker-compose.yml`, `bootstrap.sh`, `install-linkding.sh`, `supervisord-tasks.conf`, `.devcontainer/`, `.env.sample`) and its documentation site (`docs/`, with its own `package-lock.json`) stay as they are. The image uses none of them; `docs/` is neither built nor copied into it.

## What Tofu changes

- `Dockerfile` and `tofu-entrypoint.sh` (new): see "How Tofu runs it".
- `.dockerignore`: lets `tofu-entrypoint.sh` into the image. Upstream's file leaves out every file it does not name.
- `bookmarks/settings/tofu.py` (new): `from .prod import *`, then:
  - When `DATABASE_URL` is a `postgres://` or `postgresql://` address and `LD_DB_ENGINE` is not set: `DATABASES` from it. Host, port, user, password and database name are taken from the address (user, password and name percent-decoded); the address's query (`sslmode=require`) becomes libpq connection parameters; upstream's `LD_DB_OPTIONS` are added. Tofu's `DATABASE_URL` goes through a transaction pooler, which keeps no server-side cursor and no prepared statement from one transaction to the next, so server-side cursors are off (`DISABLE_SERVER_SIDE_CURSORS`) and psycopg prepares nothing (`prepare_threshold` `None`, also Django's own default; Django's psycopg 3 cursors bind parameters on the client). Each worker keeps its connection for a minute, checked before reuse (`CONN_MAX_AGE = 60`, `CONN_HEALTH_CHECKS`). `LD_DB_ENGINE`, `USE_SQLITE` and `USE_SQLITE_ICU_EXTENSION` follow, because `base.py` decides them from the database it configured, which without `LD_DB_ENGINE` is SQLite: upstream's `enable_wal` would otherwise send a SQLite `PRAGMA` to PostgreSQL and stop the start.
  - `SECRET_KEY`: see "The secret key".
  - `SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")`, and `USE_X_FORWARDED_HOST` on unless `LD_USE_X_FORWARDED_HOST` says otherwise. Tofu serves the copy over HTTPS through its own proxy, and Django's CSRF check compares every form's `Origin` with the scheme and host it reads from the proxy's headers, or with `LD_CSRF_TRUSTED_ORIGINS`.
  - `SESSION_COOKIE_SECURE` and `CSRF_COOKIE_SECURE` (upstream: off).
  - What upstream keeps as files on the server's disk is off: uploading files to a bookmark (`LD_DISABLE_ASSET_UPLOAD`), HTML snapshots (`LD_ENABLE_SNAPSHOTS` off), favicons and preview images (`LD_DISABLE_FAVICONS`, `LD_DISABLE_PREVIEW_IMAGES`). See "What works differently on Tofu".
  - `LD_DISABLE_VERSION_CHECK` and `LD_INITIAL_SUPERUSER_HINT` on.
- `uwsgi.ini`: it set `DJANGO_SETTINGS_MODULE=bookmarks.settings.prod` whatever the environment said, and now sets it only when no `DJANGO_SETTINGS_MODULE` is set (`if-not-env`), which is upstream's case; Tofu's image sets `bookmarks.settings.tofu`.
- `bookmarks/settings/base.py`: the four new switches (`LD_DISABLE_FAVICONS`, `LD_DISABLE_PREVIEW_IMAGES`, `LD_DISABLE_VERSION_CHECK`, `LD_INITIAL_SUPERUSER_HINT`), off. With them off, as in upstream's development and test settings, linkding behaves exactly as upstream does.
- `bookmarks/services/tasks.py`, `bookmarks/views/contexts.py`, `bookmarks/forms.py`, `bookmarks/views/settings.py` and `bookmarks/templates/settings/general.html`: with `LD_DISABLE_FAVICONS` or `LD_DISABLE_PREVIEW_IMAGES` on, the settings page and its form leave "Enable Favicons" (with "Refresh Favicons") or "Enable Preview Images" out, no task loads one, and no page shows one, whatever a profile says. With `LD_DISABLE_VERSION_CHECK` on, the settings page shows the version without asking GitHub for upstream's latest release.
- `bookmarks/views/auth.py` and `bookmarks/templates/registration/login.html`: with `LD_INITIAL_SUPERUSER_HINT` on, the login page says how the first account is made while there is no account at all, and then, until somebody has signed in, which username and password to sign in with (see "The first account").
- `bookmarks/templates/bookmarks/details/form.html`: a bookmark's details show the "Files" section only when the bookmark has a file or one can be added. With uploads and snapshots both off it was a heading with nothing under it. With upstream's defaults it always shows, as before.
- `bookmarks/management/commands/tofu_close_data_api.py` (new): see "The database's Data API".
- `bookmarks/tests/test_tofu_switches.py` (new): each switch on, on upstream's test settings, beside upstream's behaviour with it off; and `tofu_close_data_api` on SQLite (see "Verification").
- `uv.lock`: six locked packages move to versions past advisories GitHub published after upstream's last commit, because a copy does not follow upstream: djangorestframework 3.17.2 to 3.18.3 (among others, an `Accept` header that costs seconds of CPU before any sign-in, fixed in 3.18.2), urllib3 2.7.0 to 2.8.0 (an unbounded chunk-size line and a loop in chunked deflate streams, both reachable when linkding reads a bookmarked page), certifi 2025.11.12 to 2026.10.23 (root certificates with compromised intermediate keys removed), PyJWT 2.13.0 to 2.15.1 (used by OIDC sign-in only), Django 6.0.7 to 6.0.9 (the same release line; its fixes are for GeoDjango, which linkding does not use) and soupsieve 2.8.4 to 2.9 (selector-parser ReDoS; linkding passes BeautifulSoup no CSS selector). Only those packages' lines change. Every open Dependabot alert on `master`'s `uv.lock` (upstream's) is for one of the six versions replaced here; the root `package-lock.json` has none, and the others are for `docs/package-lock.json`, the documentation site, which the image neither builds nor contains.

Nothing upstream was removed. Tofu's safety check has no finding on the repository, upstream's GitHub Actions workflows included (see "Verification"). Those workflows run only for upstream's `master` and pull requests, or by hand, so pushes to `tofu` and its tags start none.

## The first account

- linkding has no sign-up and no setup page: its accounts are made by its administrator, and the first one comes from the settings `LD_SUPERUSER_NAME` and `LD_SUPERUSER_PASSWORD` when the app starts. So nobody who opens a new copy can make an account in it, or become its administrator, before its owner does.
- Until there is an account, the login page says so: "This linkding has no account yet", and how to make it. The owner opens the app's **Keys & settings** page on Tofu, saves a value named `LD_SUPERUSER_PASSWORD` (their password) with **Hide this value after saving** on, and deploys the app again. The start then creates the account `admin` with that password, an administrator (superuser and staff). Sign in with `admin` and the password.
- Once that account exists, and until somebody has signed in, the login page says "Nobody has signed in to this linkding yet": sign in with the username `admin` (or the `LD_SUPERUSER_NAME` you saved) and the password you saved as `LD_SUPERUSER_PASSWORD`, and, if that password does not work, the way back below. An owner who saves the password before first opening the copy sees only this notice. It names only the default, `admin`, never a name saved as `LD_SUPERUSER_NAME` (the owner reads that back on the Keys & settings page; a hidden value cannot be read back), and it goes away at the first sign-in, which Django records as the account's last login.
- `LD_SUPERUSER_NAME`, a public setting, names the first account instead of `admin`. Save it together with the password: with `LD_SUPERUSER_NAME` and no `LD_SUPERUSER_PASSWORD`, upstream creates that account without a usable password (for OIDC or an authentication proxy), and nobody can sign in to it with a password.
- Both are read only while that account does not exist. Changing `LD_SUPERUSER_PASSWORD` later changes nothing: change the password in linkding (Settings, then "Change password"). An owner who has lost or mistyped their password saves a new `LD_SUPERUSER_NAME` together with a new `LD_SUPERUSER_PASSWORD` and deploys again; that makes a second administrator, who can set the first account's password under **Admin** (`/admin/`), Users. Until the first sign-in, the login page says this too.
- Other people's accounts are added by an administrator under **Admin**, Users.
- linkding does not slow down or lock out repeated failed sign-ins; it answers each with 401, for tools like Fail2Ban, which a copy does not run. Use a long password.

## The secret key

- Django signs sign-in sessions with `SECRET_KEY`. Upstream keeps it in `data/secretkey.txt`, made at the first start; a copy has no lasting disk, so that file would be new at every restart and sign everyone out. Tofu supplies no key, so a copy derives one at every start: the SHA-256 of `linkding-secret-key:` followed by the whole `DATABASE_URL`, written as 64 hex characters.
- Anything that changes `DATABASE_URL` changes the key at the next start: a new database password, a different host or pooler address, other query options, or a database Tofu brings back or creates anew under another address. After that start everyone is signed out once and has to sign in again. Accounts, bookmarks, API tokens and feed tokens are kept in the database and are not affected.
- To keep sessions independent of the database address, save `LD_SECRET_KEY` as a hidden value on the app's Keys & settings page (for example the output of `openssl rand -base64 48`) and deploy again; that change signs everyone out once.
- The derived key is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.

## The database's Data API

- Tofu's databases are Supabase PostgreSQL. On one whose default privileges still give every new table in the `public` schema to the roles of Supabase's Data API (`anon` and `authenticated`), as every database Tofu created before 2026-10-30 does, anyone holding the project's public key could read and change linkding's tables through that API: accounts with their password hashes, sessions, API tokens and bookmarks.
- So at every start, after the migrations, `manage.py tofu_close_data_api` turns on row-level security, with no policy, for linkding's own tables (every table of its installed apps, and Django's record of applied migrations) that linkding's role owns and that do not have it yet. Those roles then see no row. linkding's own connection owns the tables, and row-level security does not limit a table's owner.
- It only ever turns row-level security on, touches no other table, and does nothing on a database without those roles. If it fails, the start logs `tofu-entrypoint: could not turn on row-level security for linkding's tables` and goes on. On a new database the log says `Turned on row-level security for 21 of linkding's tables for Supabase's Data API`.

## What works differently on Tofu

- **No favicons and no preview images.** Upstream can show each site's icon and an image next to every bookmark (both off until a user turns them on in Settings). It downloads them, the icons by default through a Google service, into `data/favicons` and `data/previews` on the server's disk and serves them from there. A copy has no lasting disk: the next restart would lose every file while the database still names it. On a copy, Settings has neither choice and no bookmark shows either.
- **No files on bookmarks.** Upstream lets you upload a file to a bookmark and keeps it in `data/assets`. On a copy a bookmark's details have no upload, and the REST API's uploads (`/api/bookmarks/<id>/assets/upload/`, `/api/bookmarks/singlefile/`) answer 403 `Asset upload is disabled.`
- **No HTML snapshots.** Upstream's `linkding-plus` image saves a copy of each bookmarked page with Chromium, into `data/assets`. A copy's image has no Chromium, and the switch stays off.
- **The Internet Archive integration works.** It is off until a user chooses "Enabled" for "Internet Archive integration" in Settings; then every new bookmark is saved on the Wayback Machine (web.archive.org) by a background task, and its details link to that snapshot. Without it, the details link to the Wayback Machine's page for the address.
- **Background tasks keep their queue on the container's disk.** Huey keeps queued tasks in a SQLite file in `data/`. A task that has not run yet when the copy restarts is lost: an Internet Archive snapshot, or a title and description refresh. With more than one instance of the app running, each has its own queue and runs the tasks queued there.
- **No update check.** The settings page shows the version (`1.47.0`) without asking GitHub for upstream's latest release: a copy does not follow upstream.
- **No mail.** linkding sends none, so there is no password reset by mail; an administrator sets passwords under **Admin**.
- **Sharing is upstream's.** A user who turns on sharing, and then public sharing, in Settings can mark bookmarks shared; publicly shared bookmarks are visible to anyone at `/bookmarks/shared` and in the public feed `/feeds/shared`. Both are off until a user turns them on.
- **Migrations run at every start.** Two instances starting at the same moment on a database that is behind would both try to apply the same migration; in the one that loses, PostgreSQL rolls that migration back whole, and `tofu-entrypoint.sh` runs `migrate` again five seconds later, when there is nothing left to apply.
- Upstream's links in Settings (its GitHub repository, documentation and changelog) and to its browser extension stay as they are. MIT asks a copy for no source offer.
- `/health` answers 200 with the version, as upstream's.
